# 战斗系统深化 · 调研与设计笔记

> 2026-09-19 这一批「战斗系统深化（后端逻辑层）」的调研底稿与决策记录。
> 结论一律附来源；每一条设计都能指到 src/lib/battle/ 里的一个函数与 tuning.ts 里的一个开关。
> 演出 / UI 那一半本轮没做（另一个批次接手），文末列了接口点。

---

## 0. 一句话结论

回合制的「深度」几乎不来自数值，而来自**三条互不相同的资源**在同一段时间里互相喂：
一条产、一条耗、一条是把敌人的壳敲开换来的窗口。本仓原本只有前两条（节拍 / 共鸣槽），
第三条（敲开破绽换来的合力）敲完就散了 —— 这一批补的就是它。
敌人一侧同理：聪明不等于更强，「每次都出最重的那一手」等于偷偷给对面加 1.35 倍输出，
那一下实测把卷末胜率从 83% 压到 70%（见 §5 的调参日志）。

## 1. 调研：回合制战斗机制（连携 / 破防 / 资源循环 / 属性克制）

### 1.1 「弱点 + 层数 + 打穿后的窗口」是被反复验证过的同一形状

《歧路旅人》：

> 敌人有各自不同的武器或属性弱点和数层护盾。玩家需要用相应的弱点武器或属性击破护盾。
> 敌人的护盾被全数打破时即进入 BREAK 状态暂时不能行动，此时角色攻击敌人可造成较大伤害。
> 此外角色每回合均可获得 BP（Boost Point），使用积攒的 BP 可以打出多段攻击或是使出更强力的技能。

> 来源：<https://zh.wikipedia.org/wiki/%E5%85%AB%E6%96%B9%E6%97%85%E4%BA%BA>

要点三条，逐条对应到本仓：

1. **弱点要分条**：不是「谁伤害高打谁」，而是「谁对得上这条轴」。本仓的 guardAxis / axisHits 已是这一条。
2. **层数让多段技有独立价值**：段数与轴是两把不同的钥匙。本仓 SkillSpec.effect.hits 与 stripGuard 一次削一点，已是这一条。
3. **打穿之后要有一个窗口，而且这一笔要被记下来**：这是本仓原先缺的一环（见 1.3）。

《崩坏：星穹铁道》给的是同一个形状的另一版，而且把**资源循环**也串了进去：

> 每个敌人都有一种或多种元素属性作为其「弱点」，使用其弱点属性攻击可降低敌人的「韧性」，
> 韧性耗尽后将对敌人造成「弱点击破」效果，使敌人受到额外伤害并遭受减益，一回合后恢复韧性值。
> 每个角色可在战斗中使用两种技能：「战技」和「终结技」。战技需要消耗「战技点」释放，
> 发动普通攻击可获得战技点；终结技则是需要清空「能量」才能使用的绝招，普通攻击和战技均可累积能量。

> 来源：<https://zh.wikipedia.org/wiki/%E5%B4%A9%E5%9D%8F%EF%BC%9A%E6%98%9F%E7%A9%B9%E9%93%81%E9%81%93>

它把三件事分得很干净，这也正是本仓该照的分法：

- **破防的门槛**（弱点属性）—— 决定「打得开吗」；
- **窗口的长度**（一回合后恢复）—— 决定「打得完吗」；
- **出手的本钱**（战技点产耗）—— 决定「这一手我出不出得起」。

本仓对应的是 guardAxis / guardMend / tempo，三样都在，但**第一样敲开之后没有回报**：
敲穿只换来「停一拍 + 挨打 ×1.5」，而且是一次性的，没人接着用。

《星之海》的战斗系统分析把这条链写得更细，还给了「窗口之后怎么接」的答案：

> 战斗中的大多数战斗行动都能使组合技槽增长（左下黄槽），破锁的增长数值最多（破1格锁与3次普攻的增长值相当）。
> 组合槽满后会转换为组合技点数，供角色使用。
> 组合技除了伤害/加血数值高以外，更关键的是提供更多样的伤害类型组合方式，提升破锁效率。
> 某些怪物的技能锁，只有通过组合技才能全破。

> 来源：<https://www.gameres.com/forum/t/908772>

**这一段是这一批改动最直接的依据**：破锁的那一笔不只换来伤害，还换来**一种新的资源**
（组合技点数），而那种资源反过来又能更快地破锁。闭环于是成立：
破锁 → 点数 → 更强的破锁 → 更快的破锁。

本仓原先缺的正是这一步「换成资源」：敲穿破绽只回一点节拍（TUNING.breakTempo），
那是把回报折成同一种货币，于是「读轴」与「堆伤害」最后走的是同一条路。

同一篇还给了一条关于**倒地**的设计（与本轮无关，但下一批做演出的人该知道）：

> 战斗中角色HP归0后不会直接死亡退场，而是会暂时倒地……在双方行动轮次后，倒地角色会直接起身并回复50%HP。

本仓的「战斗续行 / 不倒」（keepStanding）走的是另一条更贴原作的路（一次机会，不是自动起身），
这一处**不建议**照搬 —— 记在这里只作对照。

### 1.2 属性克制：别把「对轴」做成倍率表

上面三个来源的共同点是：**克制关系不落在伤害倍率上，而落在「能不能推进那层壳」上。**
这与本仓现状一致（damageOf 里只有「物理抗性」那一笔固定装甲，轴只影响 stripGuard 与 linkPow），
所以本轮**没有**新增任何属性倍率表 —— 那会把「读轴」退化成「看数值」。

旁证：《最终幻想XIII》用「阵式」把「这一轮由谁来做什么」做成一层可切换的编队资源，
而不是给每个角色一张克制表：

> 本作使用了快节奏的新战斗系统，通过「水晶盘」决定角色能力的发展，并使用了可定制的「阵式」系统来控制角色所使用的能力。

> 来源：<https://zh.wikipedia.org/wiki/%E6%9C%80%E7%BB%88%E5%B9%BB%E6%83%B313>

这一条本轮**没有**落地（阵式 = 预设队伍策略，需要 UI 配合，属下一批）。

### 1.3 本仓的缺口（调研之后回头读自己的代码得出的）

| 机制 | 现状 | 缺口 |
| --- | --- | --- |
| 破绽（guardPts / broken） | 完整（削点 / 打穿 / 停拍 / 挨打加成 / 尽碎 / 重凝） | 敲开之后那一笔**没有去处** |
| 节拍（tempo） | 完整（六道恢复途径，2026-09-16 砍过一轮） | 够用 |
| 共鸣槽（follow） | 完整（一人一条，全员满才成立） | 它只增不减地「等」，玩家改不了节奏 |
| 双人追击（followCondition） | 两条条件（破绽 / 咏唱） | 两条都是**顺风**条件，逆风时一次都不亮 |
| 敌方出手 | pickTarget 三条规则 + 重手 35% 随机 | 没有集火、没有治疗、没有换招 |
| 首领 | 阶段切换（phaseTwo，换个人）+ 终结技咏唱 | 没有「同一个人打红了眼」那一层 |

## 2. 调研：多阶段首领的设计

### 2.1 阶段切换要有叙事正当性，否则就是「数字变大」

> Dark Souls 的 Ornstein and Smough 是最清楚的例子：杀掉其中一个，另一个会明显地吸收倒下搭档的力量 ——
> Smough 变大变慢、成为纯粹的威胁，或者 Ornstein 借来雷电、快到接近 Smough 原来威胁的样子。
> 没有一个单独的过场解释这个跳变，因为**吸收本身就是那个跳变**。
>
> 失败案例是狂暴计时器（enrage timer）：血量跨过一条线，伤害与速度上升，
> 而场地的变化、招式的质地、首领被呈现出的角色，一样都没变。
> 判定标准是同一个：你能不能**用一句话**说清，这位首领受伤之后为什么打法不一样？
> 如果那句话是「它更生气了」，你拿到的是一个狂暴计时器，不是一个阶段。

> 来源：<https://comp4020-agentic-coding-studio.github.io/comp4020-ass2-YanZZZZZZZZ/lectures/week-05/>

**这一条直接决定了本轮的取舍。** 本仓已有 phaseTwo（换人：巨匠 → 黑之魔王 → 二级天使・百翼，
档案里写着 next 链，且原文里军团随本体意志散去）—— 那是合格的「阶段」。

本轮新增的 checkEnrage **不是**在已经有阶段切换的地方再叠一个纯数值狂暴，而是：

1. 只对 tier（精英 / 首领）或 namedId（指名首领）生效，杂兵不发脾气；
2. 一个形态只狂暴**一次**（Combatant.enraged 计数；换形态就是新的 Combatant，各算各的）；
3. 它**必须给对价**：enrageGuardOpen 让它在同一拍把破绽整个掀开（guardPts = 0 + guardMend），
   于是「它更凶了」这件事同时是「它这一段没有壳了」。

第 3 条就是用来回应上面那段「enrage timer 是反例」的批评 —— **纯数值变大的狂暴不许进这个仓库**，
要么带一个可读的窗口，要么它就该是一个阶段。

### 2.2 Boss 战是一个故事，而且必须给 Boss 一套「不被锁死」的手段

> 就像传统故事叙事学那样，Boss战往往应具备「开端」「发展」「高潮」「结局」这四大阶段。
>
> 第四步，设计Boss的防御机制。Boss战中一个常见的漏洞就是玩家把它保持在某种使它所有攻击不能生效的状态下击杀。
> 如果玩家可以做到这个，那你所设计的一切都将付之东流。
> 为了避免这种情况出现，你需要赋予Boss防御的能力以便他可以从战斗中撤离或是使它的攻击不能被中断。

> 来源：<https://www.chuapp.com/?a=index&c=Article&id=193703>

对本仓的两条直接约束（也写进代码注释了）：

- **不许把「停手」做成唯一解**：breakTicks 压死在 1、stallCap 压死在 1，都是同一条教训的历史痕迹；
  本轮新增的「同调」削破绽也只削点数（syncGuardStrip = 1），不做「归零 + 不许重凝」那种一刀切
  （那是 guardClear 的专属活，且只有 1 回合）。
- **首领要能自救**：foeplan 的危机应对（foeCrisisAt）让残血首领先给自己套一层，而不是站着挨打 ——
  这就是「给它防御能力」的最小落点。

### 2.3 集火 / 治疗 / 换招：三件「读得出来的行为」

这三件没有单一权威出处，是从上面几篇共同的观察推出来的：《星之海》那篇里怪物的技能锁要求玩家
「综合考虑诸多因素后，找到破锁最优解」，说明敌人那一侧是有明确意图的；而玩家读得出意图，才谈得上最优解。

- **集火**：几只敌体咬同一个人 —— 它让「谁掉血快」有因果，而不是随机分布；
- **治疗**：敌方也会把出手交给队友而不是自己 —— 它让「先杀奶」成为一条真策略；
- **换招**：同一招连着放要打折 —— 它让敌方的招式表不是装饰。

⚠️ 但**频率不许动**。这是本轮最重要的一条实测结论，见 §5。

## 3. 调研：galgame / AVG 式的战斗演出节奏（本轮不实现，交给下一批）

### 3.1 演出是「屏幕边界」与「景别」的游戏，不是特效堆叠

> 对于「直死之魔眼」、充血、头晕目眩这样直观的特效，和表现运动感和位置关系的对白，以及战斗镜头设计都非常出彩。
>
> 典型方法一：背景和人物分离 …… 《月姬》在使用这个技巧的时候，通常会给背景图的上下两侧加上非常明显、粗壮的黑边遮罩，
> 以表示现在背景图和人物的分离关系，因为人物的立绘明显超出了背景图的显示范围。
> 月姬用黑边遮罩背景图，是人为地创建了一个「屏幕」——图像边界的概念。

> 来源：<https://www.gcores.com/articles/196861>

可摘出的三条（下一批设计作战屏演出时可直接用）：

1. **景别是节奏手段**：近景打「这一下」，全景打「这一轮」。本仓作战屏的多敌排布天然是全景，
   所以「连携 / 同调 / 狂暴」这三类**全队级**事件才该用全景处理，单点伤害用近景。
2. **黑边 / 遮罩 = 人为的屏幕边界**：把「战斗盘」与「对话框」分开，比任何模糊与光晕都有效。
   本仓的 token 规矩（backdrop-filter 全站 0 处、浮层靠 72% 遮罩压住）与这一条同源。
3. **台词与特效错开一拍**：先出画面、后出台词，眼睛才有时间读完数字。

### 3.2 「手 K 演出」的成本是真实约束

> 37个图层与1200行代码：视觉小说的「手K演出」到底在肝什么？

> 来源：<https://www.cngal.org/articles/index/9471>

这一条不是设计结论而是**工程结论**：逐帧手做演出的成本高得离谱。
所以本轮把「演出该说什么」做成了**数据**（日志条目的 skillId 分类、link 载荷、sync / enrage 独立日志行），
下一批做演出的只需要消费这些稳定 id，不必回头改引擎。

### 3.3 本仓已有的节拍器（下一批别重复造）

- 战报是一行一行读的（pushLog），**日志的次序就是演出的次序**；
- 有 tone（strike / …）与 scope（one / all）两个字段可以驱动镜头；
- 有 link 载荷（参加者 + 招式名）可以直接撑起右侧那张连携牌；
- 本轮新增 foeplan.foeModeName(mode) 与 engine.linkBoardOf(s)，是给「敌方意图挂牌」与「连携条件表」用的。

## 4. 落地：机制清单（文件 / 函数 / 开关）

### 4.1 连携点（第三条资源循环）—— src/lib/battle/engine.ts

| 位置 | 做什么 |
| --- | --- |
| gainChain(s, n) | 进账：夹在 chainMax 内，进账即把空转拍数清零，并记峰值 |
| chainOf(s) | 只读：{ cur, max, frac }，给屏上画条 |
| chainLinkMul(s) | 合击倍率：1 + cur × chainLinkPerPoint，封顶 chainLinkCap |
| fireSync(s) | 攒满那一拍自动放「同调」：全队攻 / 速 / 减伤几拍 + 全体敌体破绽各削一点 |
| stripGuard | 我方敲穿破绽 → +chainGainBreak |
| clearGuard | 破防尽碎 → +chainGainCrush |
| hit | 我方打掉一个 → +chainGainDown（真倒下才算；续行 / 不倒不算） |
| phaseTwo | 打穿一个首领形态 → +chainGainPhase |
| endBeat | 先判「同调」，再判漏点（chainIdleBeats）—— 顺序反了就永远攒不满 |
| fireLinkHand | power 与 linkPow **同乘** chainLinkMul |

开关：chainOn（总）、chainMax、chainGainBreak / Crush / Down / Phase、chainIdleBeats、
chainLinkPerPoint、chainLinkCap、syncAtk / Spd / Shield / Turns / GuardStrip。

为什么 power 与 linkPow 必须同乘：连携总量是 0.75 ×（参加者各人该轴读数之和）（synergy.LINK_SHARE），
只乘一边会让「谁先动」改变同一记连携的分量 —— 那是 bug，不是设计。

### 4.2 连携条件可枚举 —— synergy.ts + engine.ts

| 位置 | 做什么 |
| --- | --- |
| synergy.linkCondsOf(ids, bond) | 把每条连携的**触发条件**摊成人话（kind 为 gauge 或 cond） |
| engine.linkBoardOf(s) | 补上此刻的进度：槽攒到几拍、冷却剩几拍、谁不在场、blocked 一句「还差什么」 |
| followCondition | 新增**第三条**条件：同伴残血时接应（linkRescueOn / linkRescueAt） |

⚠️ linkBoardOf 是**只读**的：判定仍在 linkReady / followCondition 里。
两处各写一套判据的话，屏上的读数与实际接不接得上迟早会打架。

### 4.3 敌方 AI —— 新文件 src/lib/battle/foeplan.ts + engine.enemyAct

planFoeAct(s, foe) 只读盘面，返回「打谁 / 动哪一记重手 / 要不要先治先护」；
engine.enemyAct 负责执行（扣节拍、结算、写日志）。执行次序写死在 enemyAct 头注里：
咏唱 → 召唤 → **规划** → 老路兜底。

| 行为 | 判定 | 开关 |
| --- | --- | --- |
| 治疗 | 友军 hpFrac ≤ foeHealBelow | foeAI + foeHealBelow |
| 危机应对 | 自己 hpFrac ≤ foeCrisisAt 且有保命手 | foeCrisisAt |
| 集火（补刀式） | 有人 hpFrac ≤ foeFocusBelow 才咬住，咬住后不松口 | foeFocusOn / foeFocusBelow |
| 换招 | 上一手那一招打折 foeSwapPenalty；对上目标破绽轴加分 foeBreakWeight | 同上 |
| 重手频率 | **仍由 engine 掷 foeHeavyRate（0.35，与原版同值）** | foeHeavyRate |

分工是死的：规划器只决定「打谁 / 哪一记重手」，多重手那枚硬币归 engine：

```
k = heavy && Math.random() < TUNING.foeHeavyRate ? heavy : basic
```

### 4.4 首领 · 狂暴与破防窗口 —— engine.checkEnrage

hit 里挨完一下判一次：enemy + （tier 或 namedId）+ hp ≤ hpMax × enrageAt + 本形态没狂暴过，
则破坏力 ×(1+enrageAtk)、充能 ×(1+enrageSpd)（**直接改 axes / spd，不挂 buff**），
并把破绽掀开（guardPts = 0，guardMend = guardClearRounds）。

为什么不挂 buff：addBuff 的时限是「本人出手次数」与 buffRoundsCap 回合两者取先到，
而狂暴该挂到**这个形态结束**。挂 buff 的话，活得久一点的首领会在十几拍后自己冷静下来 ——
那不是狂暴，那是一阵心慌。（与 SkillForm 变身同一条路数：直接改面板。）

开关：enrageOn、enrageAt、enrageAtk、enrageSpd、enrageGuardOpen。

### 4.5 战果 → 主线的数据侧 —— settle.ts + narrate.recordOf + types.BattleRecord

| 位置 | 做什么 |
| --- | --- |
| narrate.recordOf | 多写 7 个可选字段：chainPeak / syncs / phases / enraged / breaks / ties / bossId |
| settle.plotTieInOf(rec) | 纯函数：{ mainline, won, tier, flags, lines } —— flag 一律 battle. 前缀 |
| settle.tieLineOf(rec) | 同上，一句话版（短信 / 简报 / 旁白） |

**调用方一个字没动**（src/views/** 本轮禁改）：这两个函数现在的读者是 0，
它们是给下一批「战斗与主线剧情联动」留的入口。旧档没有这些字段一律按 0 / 1 处理，不会抛。

## 5. 数值实测与调参日志（同一组 seed / 同一套 60 轮档）

### 5.1 总体胜率（node scripts/balance.mjs，三档各 60 轮）

| 组态 | 开局 | 中盘 | 卷末 | 卡死 | 备注 |
| --- | --- | --- | --- | --- | --- |
| **改动前（基线）** | 85% | 92% | 83% | 0 | 本表这一列即改动前的对照读数 |
| 新机制全关（chainOn / foeAI / enrageOn / linkRescueOn = false） | 85% | 92% | 84% | 0 | **证明开关能把改动整个关掉** |
| 全开 · 第一版（规划器恒出最重手 + 完美集火） | 77% | 79% | 70% | 0 | 不可接受：等于偷偷给对面 +35% 输出 |
| 全开 · 保留 foeHeavyRate 0.35 | 80% | 84% | 76% | 0 | 频率归位，仍因完美集火掉 |
| 全开 · 集火改「补刀式」（foeFocusBelow 0.6） | 82% | 86% | 77% | 0 | |
| 全开 · 再调 foeHealBelow 0.55→0.45、enrageAtk 0.30→0.22 | 80% | 86% | 77% | 0 | 收益有限 |

| **全开 · 终版**（syncAtk 0.25→0.30、syncTurns 2→3） | **85%** | **88%** | **81%** | **0** | 相对基线 −0 / −4 / −2 |

验收判据逐条：

- **总体胜率不劣化超过 8 个百分点**：−0 / −4 / −2 → 通过；
- **卡死 0 场**：三档全 0 → 通过；
- **危险度 1–4 胜率 ≥85%**：开局 100 / 100 / 100 / 100、中盘 100 / 100 / 100 / 100、卷末 100 / 100 / 100 / 100 → 通过；
- **平均拍数不翻倍**：逐档最坏 12.4（改前 13.5）、卷末危险度 9 是 10.9（改前 14.4）→ 通过（普遍**变短**）；
- 唯一新冒出来的一条报告告警：卷末危险度 9 从 46% → 45%，正好踩到报告里「低于 45%」那条线
  （与基线同一个数上，属蒙特卡洛噪声量级，见下）。

⚠️ 这把尺子是蒙特卡洛的（盘面种子化，暴击 / 浮动 / 闪避走 Math.random），同版本连跑差 1–2 个百分点。
所以「−4 / −2」要按「基本无差别」读，不要按「精确 2 个点」读。

### 5.2 机制触发频率（48 场探针，同 seed 矩阵）

| 读数 | chainMax 6 | 4 | **3（终版）** |
| --- | --- | --- | --- |
| 每场「同调」次数 | 0.00 | 0.17 | **0.27** |
| 每场合击次数 | 1.71 | 1.67 | 1.75 |
| 每场狂暴次数 | 0.85 | 0.75 | 0.77 |
| 收场时池里剩几点 | 2.33 | 1.69 | 1.35 |

chainMax 为什么是 3：一回合（我方全员各出手一次）里敲穿 3~6 次是常态，写 6 的话整场都攒不满，
「同调」一次都放不出来 —— 那条循环就是死的（实测 48 场 0 次）。

| seed | 改动前 | 改动后 | 读法 |

| 20260911 | 败 · 13 手 / 2 拍 · 首领 7900 / 9911 | 败 · 22 手 / 3 拍 · 首领 6911 / 9911 | 输出更实 |

## 6. 关掉开关之后是不是回到改动前

逐条（实测见 §5.1 第二行：三档 85 / 92 / 84，与基线 85 / 92 / 83 同数）：

| 开关 | 关掉之后 |
| --- | --- |
| chainOn = false | gainChain 直接返回 0，池子停在 0；fireSync / 漏点 / chainLinkMul 全不生效 → 与改动前完全同一条路 |
| foeAI = false | planFoeAct 返回 null，enemyAct 直接进兜底那三行（重手 35% 随机）—— 那三行**原样保留** |
| enrageOn = false | checkEnrage 第一句就返回，首领不狂暴、不掀破绽 |
| linkRescueOn = false | followCondition 只剩原来那两条（破绽 / 咏唱） |
| linkBoardOn = false | linkBoardOf 返回空表（纯只读，本来就不影响判定） |
| plotTieOn = false | plotTieInOf 只返回胜负 / 档位，不产新 flag（纯数据侧） |

**说白一句**：完全关掉之后手感就是改动前 —— 但那时四大方向一个都没进，
所以「关掉」只是回滚手段，不是推荐档位。

## 7. 仍欠缺、需要下一批（UI 层 / 数据层）配合的点

### 7.1 演出 / UI（下一批）

1. **连携点条**：engine.chainOf(s) 给 { cur, max, frac }。建议画在 SP 条旁边，与「共鸣槽」区分开（那是人层，这是队层）。
2. **同调 / 狂暴的独立演出**：日志 skillId 分别是 sync 与 enrage（都是独立一行，已带完整正文）。
   这两条是**全队级**事件，按 §3.1 该用全景 + 黑边遮罩，别混进普通伤害行。
3. **连携条件表**：engine.linkBoardOf(s) → [{ id, name, kind, need, progress, cdLeft, missing, ready, blocked, conds, desc }]。
   右侧那张连携牌可以直接照着长出来，blocked 那行字就是「还差什么」。
4. **敌方意图挂牌**：foeplan 的 note 已经写进日志（skillId 为 foe-cmd，skill 为「敌方指挥」）。
   接接口那条路（command 为 ai）本来就有「敌方指挥」一行，两路读同一个 skillId 即可。
5. **首领狂暴状态**：Combatant.enraged > 0 时详情面板该多一行「狂暴 · 破防窗口」，
   战斗盘该长一枚 data-buff 标签（它不在 c.buffs 里，通用清单读不到 —— 与 no-heal / guard-clear 同一类坑）。
6. **破防窗口的视觉**：guardPts === 0 且 guardMend > 0 是「掀开且不许重凝」，
   与 guardPts === 0 且 guardMend === 0（正常重凝中）读数一样但意思不同 —— 屏上要分开。

### 7.2 数据 / 主线联动（下一批）

7. **调用 settle.plotTieInOf(rec)**：现在的读者是 0。建议在 settleWin 成功之后取一次，
   把 flags 并进 world.flags（键都是 battle. 前缀，见 flagname.snapFlagKey 的规矩）。
8. **BattleRecord.phases > 1** 是一条很强的主线信号：它意味着「对面已经换过形态了」，
   主线正文不能还照第一形态写。**建议下一批在推演提示词里显式带上这一条。**
9. **rec.ties**（本场成立的连携羁绊 id）可以点名：哪一对在这一场真的接上了，是很好的剧情由头。
10. **rec.breaks / rec.syncs / rec.enraged** 适合做「战况摘要」那一格，不必进正文。

### 7.3 平衡侧（留给下一次调数值的人）

11. **foeFocusBelow 是本轮最敏感的一格**（完美集火曾把卷末从 83% 压到 70%）。动它之前先跑 balance.mjs。
12. **chainMax 与 chainGain\* 是一组**：单独调上限而不看进账速度，很容易又变成「攒不满」。
13. **syncTurns 影响最大**（每 +1 拍约 +2~3 个百分点胜率），调它优先于调 syncAtk。
14. 报告里还有两条**旧账**与本轮无关但一直在：nana-kamiru 从不架盾 / 回血、「伤害偏低（主音）」两人 —— 属数据表问题。
